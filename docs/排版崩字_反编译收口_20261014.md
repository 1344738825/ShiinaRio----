## 二、为什么"函数都找到了"却仍不知道乱码原因

**因为我之前只做了"地址定位"，没有"读懂函数"。**

我把 `0x3a2a0` 记成"排版主函数"，把 `0x438640` 记成"控制码分派器"——这些都是**名字**，不是**理解**。
这一轮把函数体真正读完了，才看清问题的形状：**不是某一处算错，而是同一串字节被三层不同规则分别解释。**

### 2.1 完整调用链（已读懂）

```
FUN_00416f10   外层：窗口消息循环里，反复问"还有没有待绘制的字符"
  └─ FUN_004384a0   （3 指令 getter，真身 0x4384b0）
  └─ while(...) FUN_0043a2a0(状态, hdc)     ← 每次处理一个字符
       ├─ FUN_0043bd60   入口：字体/HDC 绑定、对齐
       ├─ 控制码 switch（$ * + @ _ { | } ~ 等）
       ├─ 取字符 → 合成 16 位码位
       ├─ 宽度累加 / 换行判定
       └─ FUN_004395b0(状态, hdc, x, y, &码位, 字节数)   ← 唯一落笔点
            ├─ 查字形缓存表 DAT_00539bd0（按 16 位码，步长 0x12，上限 0x400 项）
            ├─ 未命中 → GetGlyphOutlineA(hdc, 码位, ...)  向 GDI 取轮廓
            └─ 轮廓位图 → alpha 混合写入 DIB
```

### 2.2 三层各自用不同规则解释同一串字节

| 层 | 函数 | 它怎么理解字节 | 错在哪 |
|---|---|---|---|
| ① 计宽 | `FUN_0043a2a0` + `FUN_0043b840` | 用 `81-9F ∪ E0-FC` 判"双字节" | **GBK 汉字首字节 `B0-D7` 落在单字节分支** → 每字只推进 1 单元 |
| ② 取字形 | `FUN_004395b0` | 两字节**裸值**拼成 16 位当码位 | `0xB0D1` 既不是合法 Unicode 也不是合法 CP932 → GDI 找不到字形 |
| ③ 字体 | `FUN_00438100` | `CreateFontA(..., charset=0x80, ...)` | **charset 硬编码 SHIFTJIS**，与 GBK 无关 |

**这三层没有任何一层是"把宽度算错了"这么简单。**
即使把①全部 patch 成 GBK 规则，②送出的码位依然不是 Unicode，③字体依然按 SJIS 解释。
**修好一层，另外两层照旧出错——这就是"函数都找到了、乱码依然在"的真正原因。**

### 2.3 与截图对齐

截图那行：前 24 个汉字正常 → `□ r` → 第二行 `□`。

- 用**原版 SJIS 判定**把 L2 的 56 字节切开 = **46 个单元**
- 46 × 16px = **736px > 640px（行宽上限）** → 触发换行
- 换行点落在第 40 单元 = **字节偏移 49 = GBK 第 24 个字** ← 与截图完全吻合
- 换行后被切开的半截字节各自成"字符"，取到非法字形 → `□` 和 `r`

> 注：磁盘上 A/B/C 三组判定**已经 patch 成 `0xfe`**（全 EXE `cmp cl,0x81` 仅 3 处，都已改）。
> 所以这个"原版判定"的复现，解释的是**截图拍摄时**的状态，不一定等于当前状态。
> 当前状态下每行几个字，需要跑游戏实测——静态算不出来。

## 三、UIF 那条线为什么一直没反应

从 `winmm.dll` 里提出两条自禁用条件：

```
" no rules specified. disabling text processor"
" corrupt text processor api descriptor table detected. disabling text processor"
```

当前 `uif_config.json` 的 `text_processor` 节点：

```json
"text_processor": {
  "enable": true,
  "conversion_codepage": 936,
  "enabled_apis": ["@GetGlyphOutline", "@GetTextExtentPoint32", ...]
}
```

**没有 `rules` 字段** → 命中第一条 → **整个 text_processor 在启动时自我禁用**。

UIF 支持的 rule 类型：`overwrite_rule` / `replace_chars_rule` / `replace_full_string_rule` / `replace_regex_rule` / `replace_substring_rule`。

**⇒ `rules` 数组至少要写一条（哪怕恒等规则），text_processor 才会启用。**
这也解释了为什么之前挂 `GetGlyphOutlineA` / `TextOutA` 全都 0 次命中——UIF 根本没接管。

## 四、"能不能完全拆解这个游戏"

**能，但要分清"拆解"的三个档位。**

| 档位 | 范围 | 已具备的工具 | 现实成本 |
|---|---|---|---|
| **A 档：单条纵线** | 只精拆文本渲染链（约 6 个函数）| Ghidra 反编译 + frida 动态取证 | **已完成 80%**（本轮）|
| **B 档：资源与脚本层** | WAR 包结构、SCN 脚本、字符/字形表 | 已有 unpack 工具 + `scn_probe.py` | 中等（逐格式啃）|
| **C 档：全引擎** | 全 EXE ~1500 个函数 + 全部格式 | Ghidra 全量反编译可获得骨架 | **成本极高**，且对汉化无直接收益 |

**我的建议：只走 A 档，不再扩。**

理由：
1. 你的目标是**汉化**，不是移植引擎。A 档（文本渲染链）是唯一挡在"中文显示"前面的东西。
2. C 档能给你"全函数清单"，但不能替代"读懂其中 6 个"。反编译 1500 个函数 ≠ 解决问题。
3. 现在**瞎猜的边际成本已经很高**——你说得对。A 档再往下走，需要的是**动态取证**（跑游戏 + 打点），不是继续静态读。

### 具体下一步（按性价比）

| # | 动作 | 成本 | 能回答什么 |
|---|---|---|---|
| 1 | `text_processor` 加一条 `rules`（恒等规则）| 低 | UIF 通道到底通不通 |
| 2 | 在 `GetGlyphOutlineA` 前打点，打印送出的 16 位码位 | 中 | ②层到底是 `0xB0D1` 还是 `0x4F60` |
| 3 | 跑 `_probe_count.py` | 低 | 台词走 `0x3a2a0` 还是 `0x43b840` |
| 4 | 码位是裸 GBK 的话，补 GBK→Unicode 转换 | 高 | 治本 |

**这三条都跑完，才能说"乱码原因清楚了"。在那之前，静态读数只能给"结构"，给不了"答案"。**

# ShiinaRio 引擎汉化实战方法论

这篇东西来自《超催眠術学園》(ShiinaRio v2.50) 的汉化工程，2026 年 10 月 13 日到 15 日，三天。
脚本 48501 行、标题与系统 UI 图像 115 槽、编译脚本里的选项 18 条。

写下来是因为踩的坑挺有通用性：这套引擎的设计在同类日式老引擎里很常见，资源打包、自绘字体、
还有一部分文字直接烤进图像里。你要是接手同引擎的游戏，或者遇到"文字改不动"的老游戏，
希望这份记录能让你少花两天。

本库不含游戏二进制、音频、图像原资源。`tools/` 里的脚本可以复用，但路径常量写死在文件头，换项目要自己改。

---

## 0. 先建立正确的心理模型：改动面分三层

```
WAR 容器（表区 + 条目区，条目可以重名）
  └─ 条目加密（essential crypt / ypk mask，每条目一个 pos1 参数）
       └─ 内容格式（.SCN 编译脚本 / .TXT 文本 / .S25 图像包 / .OGG 音频）
```

关键是：改动必须能原路写回去，写不回去就等于没做。三层的约束完全不一样。

| 层 | 约束 | 破法 |
|---|---|---|
| 容器 | 表区长度变化会引发条目位移 | 表区可以增长，但没动过的条目必须逐字节全等 |
| 加密 | 不知道 pos1 连明文都读不出来 | 0 到 63 爆破，用格式 magic 校验（见 §1） |
| 格式 | SCN 有等长约束；S25 条目尺寸一变就弹错 | fit 精确长度对齐（见 §2、§6） |

我一开始没分清这三层，把容器问题和格式问题混在一起排查，白绕了很久。

## 1. 破解入口：pos1 爆破，以及别死磕哑块

每个条目用 pos1（0..63）参与解密。做法很朴素：

```python
for c in range(64):
    plain = decrypt_entry(raw, c)          # 可能抛异常，直接 continue
    if plain[:4] == b"S25\x00": break      # 用该格式的 magic 做判据
```

三条实测经验：

1. **判据要用 magic 加尺寸双校验**。只认 magic 会误命中，这个项目 14 个 S25 里解错了 5 个。
2. **解不出来的条目，绝大多数是哑块**。纯色占位图（BLACK/WHITE/DUMMY）、dummy 音频，
   还有一种我管它叫前缀影子的东西：真条目前面挂一个同名小条目，名字首字节被改写过，
   比如 `ﾉLACK.S25` 其实是 `BLACK.S25` 的影子。这个项目 48 个条目里 11 个解不出，全是哑块，
   真资源 37 个全解出来了。我在那 11 个上面耗过时间，纯粹浪费。
3. **条目名可以重复**，同一资源一大一小两份。所以任何对拍、写回都必须按槽位序号做键。
   用名字做键会被同名条目互相覆盖，我验收时吃过这个亏，误报了 8 条 FAIL，查了半天才反应过来。

## 2. 文本面：SCN 的等长铁律和 fit_compress2

SCN 是编译后的脚本，内部带绝对偏移。改一个字节的长度就整体错位，回放直接崩，或者弹 `Not File Type`。
所以规则只有一条：明文长度逐字节不变。

麻烦在于译文通常比原文短（日文翻中文），压缩后长度会掉，得精确补回去。

`fitlib.fit_compress2` 的逻辑：

```
目标长度 L ← 原条目的 size_comp
1) 在明文里插填充（末行注释 + 随机 hex 串），把明文撑到某个候选长度
2) zlib 压缩，看结果长度
3) 迭代搜索填充量，直到压缩后正好等于 L
```

几个要点，都是踩出来的：

- **填充要分摊到多行**。早期版本把填充全塞进一行，单行 30 万字符，回放崩了（交接文档 §29 有完整记录）。
- **填充池要够大**。EX 条目缺口 215KB，原来的 `HEX_MAX=120000` 根本不够，我放到了 2000000。
- **必须断言** `zlib.decompress(z) == plain_full` 且 `len(z) == L`，命中之后再解回来比对像素或文本。
- 代价：SYSTEM 搜了 1298 次，EX 只用了 22 次但那是 52MB 的条目，跑了十几分钟。大条目务必后台跑，
  我第一次在前台跑，直接被超时 SIGTERM 掉。

## 3. 字库面：GBK 一级区守卫（最坑的一条）

引擎的字体和字符映射表只覆盖 GBK 一级区（首字节 ≤ 0xD7）。
写进二级区的字不会报错，而是落表错位，显示成另一个字。真机上就有过一个二级区词显示成了笔画毫不相干的另一个字，
我当时以为是翻译写错了，查了半天才想到是字库区的问题。

对策三条：

1. 译文只用一级区字。
2. 每个 patch 脚本里加编译期断言：

```python
for ch in cn_text:
    b = ch.encode("gbk")
    assert b[0] <= 0xD7, f"二级区字: {ch}"
```

3. 真机复验时专门找这类字试。性描写和生僻字是重灾区，正常文本反而不会出问题。

另外两条硬校验（见 `tools/_check_tsv.py`）：非 GBK 字符、含 `0x5C`（反斜杠会被当转义，行内出现就崩）。
还有一条容易漏：中日同形行（译文等于原文）必须显式登记，否则导出器把它算成未译。

## 4. 显示层：EXE 只改了 18 个字节

前面几节都在讲怎么把中文塞进资源。塞进去之后还有一件事：引擎得认得中文。

这块当初花了我好几天，frida hook 跟反编译来回定位，才找到 Shift-JIS 解码器那个
把 GBK 引导字节误判成单字节的缺陷。但最后打在 EXE 上的补丁，只有 18 个字节、6 处：

| 文件偏移 | 原版 | 改成 | 是什么 |
|---|---|---|---|
| `0x3815d` | `80` | `86` | CreateFontA 的 charset，128(Shift-JIS) → 134(GBK) |
| `0x29c13` `0x3a9ae` `0x3ab83` `0x3bb0f` | `9f` | `fe` | SJIS 解码器边界 ×4（引擎里有三份同构的解码器） |
| `0xc1f7c`（13 字节） | `ＭＳ ゴシック` | `MSGothicCNJP2` | 请求的字体名 |

`0x3bb0f` 那处就是那个 bug：解码器把 `0xA1-0xDF` 当单字节处理、前面补 `0xFF00`，
GDI 收到就当成非法 SJIS 码位，表现是某些字显示成别的字。
把边界从 `0x9f` 推到 `0xfe`，GBK 的引导字节才被当双字节读。

`tools/patch_exe_cn.py` 做的就是这 6 处。它每改一处前先校验原字节，对不上直接报错退出，
不会写坏文件，带 `--check` 和 `--revert`。拿原版 EXE 跑一遍，出来的 md5 和我实际在用的
汉化版逐字节相同——这条我验过。

**别指望这 18 个字节能直接用在别的游戏上。** 偏移是这一个 exe 的，同引擎其他版本大概率不同。
但"要找哪几类地方"是可复用的：字体创建的 charset 参数、SJIS 解码器的字节边界、字体名字符串。
按这三类去搜，比从头摸索快得多。

字体是另一件事：EXE 里改的只是"请求哪个字体名"，字体文件本身还得有人提供。
这里用了一个覆盖 GBK 一级区的字体，命名成 `MSGothicCNJP2.ttf` 放进游戏目录，
靠 UIF（`winmm.dll` 代理注入）在运行时注册进进程的字体枚举。UIF 是第三方项目，不在本库里。

顺带一个我没查到底的事：把 `winmm.dll` 临时移走再启动，游戏照样起来，窗口标题中文也正常。
但窗口标题走的是系统字体，游戏内文本走引擎自绘，那条路径我没验，所以没有 UIF 到底会怎样我不知道。
这条别当结论用。

## 5. 排版面：引擎按整串宽度居中

选项和按钮类的文本，引擎按整串宽度算居中。于是：

- 译文短，尾部补空格，真机偏左
- 改在句首补空格，真机偏右

用户在真机上给我反馈了两轮，我才反应过来。

根治办法只有一个：译文字数和原文严格相等，零补齐。
14 对选项最后全部做到字数相等，比如 `自分本位な愛を貫くことしかできない`（17 字）
对 `只能把以自我为本位的爱贯彻到底而已`（17 字）。凑不齐字数宁可换措辞，别靠空格调位置。

## 6. 烘焙图面：文字被烤进 S25 图像怎么办

标题和系统菜单的文字是图，不是文本。流程三段。

### 6.1 擦除（最难的一段）

不能简单涂黑，按钮有渐变、描边、角饰。做法是参考带重建：

- 取文字行上下的干净像素带，用 PCHIP 逐通道独立插值，算出这里没字的话应该是什么颜色；
- 判断哪些像素是字：亮底用 `dev > 阈值`，深底用亮度阈值 `vals > median + 25`；
- 半透明阴影边缘也要纳入（alpha ≥ 100），否则留一圈灰边；
- 竖排字占满全高，水平参考带被污染，必须改成横向参考带加亮度阈值；
- 一遍擦不干净就二遍降阈（dev>5 / dark>4），清亮底的残片。

### 6.2 重画

按原图实际样式建模，先目验再批量。这个项目遇到三种：

| 样式 | 特征 | 画法 |
|---|---|---|
| 按钮（灰/橙/铜三种底） | 白字加黑投影 | 白 `#FEFDFC`，投影 alpha 0.6、偏移 (2,2) |
| 透明底消息条 | 黑字加白描边 | 字色 22，ring 膨胀 2px 填 245，alpha 必须设 255 |
| 竖排标签 | 白字，深底 | 字号 `min(w*0.5, h/(n+0.6)*0.85)`，短词必须 clamp 宽度 |

第三条那个 clamp 是我漏掉的：短词按高度算字号会太宽，直接出框。

字号通用式：横排 `min(h*0.55, w*0.9/len)`，竖排如上。

透明底那条漏设 alpha 也值得一提，整图直接变空，看不出来是 alpha 的问题。

### 6.3 回封

**S25 条目尺寸一变，引擎就弹 `Not File Type` 或 `@gload`**。这句话值得重复一遍，
因为我在 EX 条目上栽过：当时图省事直接 zlib9 重压，没走 fit，结果鉴赏模式一进去就双弹窗。

所以所有 S25 改动一律 fit 等长回封，没有例外。

## 7. 工程纪律：比技术更省时间

1. **先清后建**。先把红点和校验失败清干净再写新代码。带着脏基线往上叠，最后分不清是谁的锅。
2. **判据必须机器取证**。git status、exit code、字节数、md5。叙述性解释不算证据。
3. **幂等基线**。重封脚本一律从原始备份 BAK 出发，保证可重复执行。
   但这里有个反过来的坑：单包模式会吞掉其他包的改动。
   我跑过一次 `python _sys_pack.py EX`，结果 EX 的修复版把已经部署好的 SYSTEM 和 EXBGM
   共 115 槽翻译全冲掉了，用户第二天在真机上发现菜单还是日文。
   所以单包跑完必须再全量跑一次，或者干脆改脚本支持增量基线。
4. **禁改验收脚本去迁就实施**。验收 FAIL 就改实施代码。
5. **验收两条**：替换过的槽位解码结果等于输入图；没动过的条目 raw 与备份逐字节全等。两条都过才算 PASS。
6. 大条目打包必须后台跑。
7. 环境：托管 Python 经常缺 numpy 和 PIL，用 venv（`envs/default/Scripts/python.exe`）。

## 8. 常见误判（都是真踩过的）

| 现象 | 真相 |
|---|---|
| 5 张图编码器往返不一致 | 编码器 bug：行偏移写成相对值、漏写 `u16 row_size`、method 4 通道序应为 A,B,G,R |
| 按钮角饰像引号残迹 | 原版就有的装饰，不是残留，别擦 |
| 残影擦不掉 | 参考带被文字污染（竖排尤其），换方向取带加亮度阈值 |
| 整图变空 | 透明分支漏设 alpha = 255 |
| 全库对拍 8 条 FAIL | 用条目名做键，被同名条目覆盖了；改成槽位序号 |
| 真机显示成另一个字 | GBK 二级区字落表错位（见 §3） |

## 10. 两个附带结论

### 10.1 这游戏不需要注册表，可以当硬盘版挪

我原本以为挪目录得同步改注册表，因为那边写着 `InstPath` / `DataPath` / `InstMode`，
看起来像是装在哪就得从哪读。查下来不是那么回事：

- `DataPath`、`InstMode`、`savedata` 这几个串在游戏主 EXE 里**根本不存在**，只在 `UNINST.EXE` 里
- 主 EXE 里只有 `InstPath`，反编译出来的逻辑是 `RegOpenKeyExA(...)` → `if (LVar2 == 0)` 才去读，
  **打不开就跳过**，不崩
- 而且 `InstPath` 和 `GetCurrentDirectoryA` 是被加进同一个资源搜索路径列表的——当前目录本来就在列表里

实测：把 `HKCU\Software\Ｃ：ｄｒｉｖｅ．\超催眠術学園` 整个改名（等于没有），启动 → 进程活着、
窗口标题正常、没报错、没在别处乱建目录，而且**游戏没有自己重建这个键**（只读不写）。

存档路径用 frida hook `CreateFileA` 抓的，无注册表状态下直读 `当前目录\savedata\chosaimin_save*.bin`。

结论：整个目录随便搬，双击就能玩，什么都不用改。

### 10.2 HP.WAR 是人物立绘，不用汉化但也别删

`CHOSAIMIN_HP.WAR` 不在官方安装清单 `InstallFiles0` 里，我一度以为它是能扔的追加盘。
解出来是 284 张 `.S25`（140M），命名像 `P0101_01`、`PF0501`——回想模式的人物立绘差分。
抽了 12 张看，零文字，所以没有汉化需求。

但它是运行时要加载的资源，删了回想模式里人就没了。不在安装清单里只是因为那份清单按安装盘划分。
判断一个包能不能删，别看它在不在清单里，看它有没有被加载。

## 11. 最后

这套引擎不难在怎么改，难在改完还能不能原样装回去。
把等长、字库区、槽位键、幂等基线这四件事守死，剩下的是体力活。

我不确定这些方法在别的 ShiinaRio 游戏上能复用多少，只做过这一个项目。
pos1 的爆破范围、S25 的行共享编码这些都可能随版本变。要是你在别的版本上试过，欢迎来提 issue 纠正我。

## 2. 加密体系全解（已 100% 破解，勿重造）

### 2.1 WAR 容器布局（CHOSAIMIN_T.WAR 等 9 个包）
```
文件头 16 字节: [8]=table_offset^0xF182AD82, [0:8]=version(MK magic)
条目区: 从 0xC 开始, 每条 = head(8B: head_u32, size_orig) + data
表区: 在文件尾, 长 TABLE_M=917504 (0x38*16384), 条目表 plain 经 zlib+两层变换
条目表 slot(0x38B): name(0x20) + offset(u32) + size_comp(u32) + size_orig(u32) + time(u64) + flags(u32)
magic: head_u32 ^ 0x82AD82 ^ size_orig 前3字节 = "YPK"/"YH1"/"YLZ"
flags: &0x80000000=essential; &0x40000000=解压后crc; bit29=crc_crypt(实测01_A flags=0x80000003, 不参与)
```

### 2.2 essential crypt（条目级，0x475710 外层 / 0x4752E0 内块函数）
- `base_keys` = exe `0x4E70EC` 处 5×u32 = `{0x90dee7c1, 0x23dce3c5, 0xd3da24d9, 0, 0}`
- 内层 = SHA-1 变体（80 轮）：W[0..15]=data[44..107] BE；扩展 `buf[i-16]^buf[i-14]^buf[i-8]^buf[i-3]` rotl1；常量实际 0x5A827999/0x6ED9EBA1/0xE5C7BF8E+0xA953FD4E；写回仅 buffer[0..39]（data[4..43]）
- 尾部 crypt 循环：`[start+2, min(size,1024))`，start=0x80；LCG `0x5D588B65*x+1`；`pos1=(addend1+addend2)%64`；CK 表 64 字节；`x=rotr8(d[i]^rand,1) ^ ck[p1]^ck[p2]`；之后 `p1=x%64` 自演化
- **关键等价类**：真正决定结果的只是 `CK[pos1]` 一个字节；pos1=f(L,a,b)，a/b 只依赖 A[0],A[1] → **保持压缩长度 L 和 zlib 头不变即可继承原 pos1**，无需预测浮点（MSVC libm 与 Python ULP 差 1~3）

### 2.3 SaiminCrypt（extra crypt，native 0x476180 是分发器）
- 真身：`0x4d48fc` 处 zlib 流（8B 头 `YPK\x01`+size 0x17b7）解出 6071B 自解压代码 → 自定义字节码 VM
- 变换：`length>=0x200 && (flags&0x202)==0x202` 时 XOR 前 `((length&0x7E)|1)` 字节与 64 字节 K，再 `u32@0x104 ^= length`
- **坑**：VM index=0（不是 8），length=len(data)（不是 len-8）
- K（keystream）：`tools/saimin_keyprobe.bin`（64 字节循环，Unicorn 跑 VM 提取）

### 2.4 YPK 压缩加密
- 明文 → zlib(level9, 头 `78 da`) → dword XOR `0xB4B2B4B2`（尾字节 ^0xB2）

### 2.5 region CRC（仅启动期 keys 派生用）
- region 图 48×48×3=0x1B00；`crc32_custom(rgb)=0xF88F2135`；模拟器中零 buffer CRC=0x74CE8394 是 artifact

## 6. 裸启动错误框：已定位根因并修复（2026-10-13 结案）

**现象回顾**：双击 CHOSAIMIN.EXE（ACP=936）→ OP 后弹「エラー：インストールが正しく行われていません」。

**根因铁证链**（全部机器取证）：
1. 错误框 = START.SCN 偏移 `0x778` 的 msgbox 命令（opcode `0x0780` → handler `0x232a0`），是安装校验失败后经**条件跳转落到的**（不是检查本身）
2. 校验链（frida 逐命令追踪，`icheck3/trace.log`）：
   - opcode `0x00fa`（handler `0x2a9be`）：先做 **.text CRC32 完整性校验**（ptr=0x401000 len=653349，已通过），再写注册表根 `[0x4c2358]=HKCU` + 键名 `0xd0a99c`
   - opcode `0x00ff`（handler `0x175f0`）：`RegOpenKeyExA` + `RegEnumValueA` 枚举值名找 **"DataPath"**，找到→var0=1，否则→0
   - opcode `0x01f4`（handler `0x211b0`）：条件跳转，case op=0 语义 = **`if var0 != 0 → 跳 OK 路径(0x7c5)`**；var0=0 则落到错误框
3. frida 实时取证（`icheck4/reg.log`）：`>>> 0x175f0 存入 var 的值 = 0x0` —— **DataPath 没找到**
4. **真正根因：注册表键名代码页错位（WOW64 无关，双视图键都存在）**
   - 键名含 CP932 全角字符；游戏进程 ACP=936（GBK）
   - `RegOpenKeyExA` 按 CP_ACP=936 把 CP932 字节转 Unicode 后查找：
     `software\Ｃ：ｄｒｉｖｅ．\超催眠術学園` → **`software\俠丗倓倰倝倴倕丏\挻嵜柊弍妛墍`**
   - 该转换后键**已存在但是空壳**（2026-09-05 11:37 引擎自建，零值）；真正的 3 个值在原名键里
   - ctypes 复现（`tools/reg_forensics.py`）：`RegOpenKeyExA(CP932字节) → 0`（打开成功）但**枚举为空**
   - 推论：LE(932) 启动时转换正确所以能过；936 裸启动必失败——与 §4.2 的观察一致

**修复（优先级 1：模拟正确安装环境，零 patch，可逆）**：

## 7. 窗口标题栏 + 工具栏乱码：已定位并修复（2026-10-13，方案 B 已实施）

**现象**：936 裸启动进游戏后，主窗口标题栏是一串乱码，而不是「超催眠術学園」；工具栏「終了」同样乱码。

**状态（2026-10-13 11:2x）**：**方案 B 已实施并端到端验证通过**——重封 `CHOSAIMIN_S.WAR`，把 START.SCN 内联串由 CP932 改为 GBK 中文。备份在 `CHOSAIMIN_S.WAR.bak`。
```
实测窗口标题 = '超催眠术学园'   (GBK b3 ac b4 df c3 df ca f5 d1 a7 d4 b0)
frida: SETWINDOWTEXT bytes=[b3 ac b4 df c3 df ca f5 d1 a7 d4 b0]   ← 已是 GBK，非 CP932
```
因为是**游戏自己设的**字节，不存在"被脚本二次覆盖打回"的问题（方案 A 的 `--hold` 不再需要）。

**根因（frida 实时取证 `icheck5/title.log` + 静态反汇编双确认）**：
标题不是来自 INI、也不是 exe 里写死的明文，而是 **START.SCN 脚本命令 `op 0x07a8` → `SetWindowTextA(主窗口, CP932 字节「超催眠術学園」)`**；A 版 API 由 **Windows 内核**按 `CP_ACP=936(GBK)` 做 ANSI→Unicode 转换 → 乱码。这与正文文本（引擎自己调 `MultiByteToWideChar`）是**两条不同的转换路径**，所以正文能控、标题控不了。

```
CREATEWINDOW class=[92 c5 96 bc …] title=[92 c5 96 bc …]      BT: EXE+0x40884
             ↑ class 与 title 都是 CP932「椎名里緒 v2.50」（初始标题）
FINDWINDOW   class=[椎名里緒 v2.50] title=[超催眠術学園] → 0x0
             ↑ op 0x07b2 防多开检查；936 下同样因代码页错位返回 0，无害
SETWINDOWTEXT hwnd=0xa0e34 bytes=[92 b4 8d c3 96 b0 8f 70 8a 77 89 80]
                                   ↑ CP932「超催眠術学園」→ GBK 解码 = 标题栏乱码
             BT: EXE+0x251e8 <- EXE+0x2e7b3（stub，opcode 0x07a8）
```

**关键地址表**：

| 项 | 值 |
|---|---|
| SetWindowText 脚本命令 | exe RVA `0x251c0`（hwnd 操作数=0 时取 `[0xd09b84]` 主窗口句柄）→ IAT `0x4a1484` |
| 对应 opcode | **`0x07a8`**（stub RVA `0x2e7ad`；跳表 `0x31c50[7]`，idx 表 `0x31cc4[30]`，基址 `0x78a`） |
| 初始 class+title 缓冲区 | exe RVA **`0xba0f8`**，初值 CP932「椎名里緒 v2.50」（.data 段） |
| RegisterClassA | RVA `0x40745`，`lpszClassName = 0x4ba0f8` |
| CreateWindowExA | RVA `0x4087e`，class 与 title **都 push `0x4ba0f8`**；返回句柄存 `[0xd09b84]` |
| SETUP.INI | 运行时 **不读**（`GetPrivateProfileStringA` 全程只抓到 RIO.INI）→ 改 `GameTitle` **无效** |
| op 0x07b2 | = `FindWindowA`（handler `0x256a0`，IAT `0x4a1454`）：防多开检查，不是设标题 |

**为什么"改一个字节"解决不了**：
- `0xba0f8` 是 **class 名与标题的共用缓冲区**（RegisterClass 和 CreateWindowEx 都引用它），改它 class 会跟着变
- 更关键：即便改了初始标题，**脚本 op 0x07a8 随后会用 CP932「超催眠術学園」再覆盖一次** → 改 exe 无效
- 真正要改的是 START.SCN 里的内联串 → 需重封 `CHOSAIMIN_S.WAR`（S 包是系统脚本，改坏起不来）
- **对将来 patch 有用的边界**：op 0x00fa 的 CRC 自校验只覆盖 **.text（RVA 0x1000, len 653349, 末址 0xa0825）**；`0xba0f8` 在 .data，**不在**校验范围内 → patch .data 字符串不会触发自校验；patch .text 会

**关键技术点 1 —— 等长替换**：所有双字 UI 词 CP932 与 GBK **都是 4 字节**（标题 12→12），所以替换后**明文长度完全不变**，不动任何长度字段、不动 size_orig：

| 原文 | GBK 字节 | 等长 |
|---|---|---|
| 超催眠術学園 → 超催眠术学园 | `b3 ac b4 df c3 df ca f5 d1 a7 d4 b0` | ✅ 12 |
| 終了 → 结束 | `bd e1 ca f8` | ✅ 4 |
| 設定 → 设置 | `c9 e8 d6 c3` | ✅ 4 |

**关键技术点 2 —— 零区填充对齐（比尾部追加安全）**：S 包表区里 `size_comp` 固定，压缩后长度必须**精确等于**原值 95628 才能原地换条目。但替换会让 zlib 输出漂移（`memLevel=8` 时 95642，**超出 14 字节 → 无解**）。
解决办法：START.SCN 末尾有 **1037 字节全零区**（最后一个非零字节 @`0xb1cf7`）。往其中填不可压缩随机字节可 1:1 抬升压缩输出，**且明文总长不变**（`size_orig` 不动）——比 `warc_pack.py` 原有的"尾部追加 `\r\n;xxx\r\n`"更干净，不新增字节、不污染脚本命令流。
- 实测：`memLevel=7`（95386）+ 零区填充 **213 字节** → 压缩恰好 **95628**，head 保持 `78da`
- 注意 `zlib.compressobj(9,8,15,mem,strat)` 的 `memLevel` 是有效调节维度（1-9 输出差数千字节），`strategy` 在本例无 `78da` 组合

**⚠️ 陷阱（改其它串时必须避开）**：START.SCN 里「超催眠術学園」共 **62 处**，其中 **`0x74d`、`0xc0e` 两处是注册表查询路径**（前面紧跟全角 `Ｃ：ｄｒｉｖｅ．\`）。这两处**必须保留 CP932 字节**——因为 §6 的注册表修复正是按"CP932 字节被 GBK 转换后的键名"写入的，改了会让安装检查**再次失败**。工具按"前 20 字节含全角 `Ｃ：` 或 `software` 则跳过"来排除；其余 60 处是 VM 错误消息框标题，改中文无害。

| 表区禁加字节 | 表区 4 字节对齐多写 1-3 字节 → 游戏秒退。必须 `F[:8+len(C)]` 严格写 |
| 【女子部員Ａ】出现多次 | 全文替换要限次数（replace(old,new,1)） |
| 存档场景 | 「つづきから」读旧存档会落到未汉化 TXT（KSM/SKR/MRK 等），看到日文属正常，不是补丁失效 |

## 12. Phase 3 门禁实证：保 L 路线已定（2026-10-13）

工具：`tools/g1_probe.py`（G1 探针）、`tools/g2_sample.py`（G2 小样）。只读取证 + 输出新包，不破坏原文件。

### 12.1 G1-1 pos1 混沌性标定 —— 结论：**改压缩长度 L 不可行**

方法：对 T 包 126 条目逐个枚举 `pos1 ∈ [0,64)`，以"解压长度 == size_orig"为真值判据（zlib CRC 是强判据），与本地计算值比对得 delta 分布。

| delta | 0 | 1 | 2 | 3 | 6 | 11 | 15 | 16 | 17 | 36 | 40 | 48 | 57 | 62 | 标定失败 |
|---|---|---|---|---|---|---|---|---|---|---|---|---|---|---|---|
| 个数 | 78 | 10 | 10 | 2 | 1 | 1 | 2 | 1 | 1 | 2 | 2 | 1 | 1 | 2 | **10** |

- **26/114 = 23% 是大跳变**（36/40/62/15/48/57/16/11/17/6），不是 ±1 的小偏差
- 根因：`saimin_full.get_key_pos_addend2` 是**拒绝采样循环**（`if unk1*unk1+unk2*unk2 > 1.0: continue`、`if rand <= exp(unk1)*(unk2²+1): break`）。MSVC libm 与 Python 的浮点 ULP 差异会**改变循环次数** → 后续 LCG 消耗数全变 → 结果天差地别
- 推论：`a = s8(A[0] ^ (L & 0xFF))` **依赖 L** → L 变 → tok 变 → 采样路径变 → pos1 不可预测，**且无法本地验证**（没有真值可对照，只能实测碰运气，23% 翻车）
- **决定：放弃"改 size_comp / 重建包布局"方案。必须保 L。**
- 保 L 的正确性：L 不变 + zlib 头 `78da` 不变 → a,b 不变 → tok 不变 → **pos1 原样继承**（§2.2 等价类原理成立）

### 13.4 ⚠️ 新踩的坑：fit 的**离散跳变**

hex 填充每字符对约 **+2.1 字节**压缩输出，会**整段跳过目标长度**：

```
k=9  -> 30847      k=10 -> 30846 (反而变小!)      k=11 -> 30850
目标 30848 被跳过 —— 纯二分必然找不到
```

解法（`fitlib.fit_compress2`）：穷举 **(锚点注释行 × seed 变体 × 窄 k 区间)** 的受控搜索，带尝试预算（默认 6000 次压缩）。KYO1 实例：139 次尝试 / 0.65s 命中。
**不要在单锚点上做二分+小范围兜底**——跳变区间可能宽达 ±2。

### 13.5 ⚠️ 硬约束升级：行数零变化

原方案"尾部追加 `\r\n;hex\r\n`"会**多出 2 行**，违反"改行数会破坏 `$LABEL`/`$JUMP`"。
现在填充**写进已有的 `;` 注释行末尾**，明文行数严格不变（KYO1：3590 → 3590）。
`fitlib` 的 `_find_comment_line` 返回 24 个候选锚点；找不到注释行才回退尾部追加。

### 14.3 ⚠️ 核心发现：**中文压缩率低于日文 10~15%**

G1-2 压测用"截断明文"模拟翻译，**保留了日文的统计特性**，因此得出"必然变短"的乐观结论。真实翻译推翻了这个假设：

```
原始明文 91958 -> 压缩 30848 (33.5%)
回填32行译文后明文 91803 (-155B) -> 压缩 31136 (+288B)   ← 明文更短, 压缩反而更长!
```

根因：中文文本的 LZ77 匹配率低于日文（日文假名/助词/固定句式重复度高）。

**解法：`--strip-comments` 腾挪空间** —— 把 comment 行内容清空但**保留 1 字节 `;`**（既是合法注释行引擎忽略，又是 fitlib 的填充锚点）。KYO1 腾出 968 字节明文，fit 立即成功。

## 15. 中文显示问题：深度取证总结（2026-10-13 15:00-15:50，未解决）

用户报告：即使 T 包内是正确的 GBK 中文（已验证），游戏内中文仍全部显示错误。
本轮做了 9 轮 frida 动态取证 + 2 次运行时补丁实验，结论如下。

### 15.1 已确证的事实链（全部机器取证）

1. **数据层 OK**：游戏目录 T 包 KYO1 = 正确 GBK 中文（字节级 175/175 核对一致）。
2. **字体已生效**：GGO 时 DC 上选中的字体 face = MSGothicCNJP（exe 字体名 patch 生效）；
   GDI 直接测试该字体「图菖桃术馆」字形全有。**字体不是问题**。
3. **引擎文本解码机制**（RVA 0x3bb00，SCN 文本逐字解码器，反汇编确证）：
   - SJIS 判定：首字节 0x81-0x9F / 0xE0-0xFC → 双字节；**0xA1-0xDF → 单字节**
   - 双字节 → 字节对原样传下游（`mov ax,[eax]` @0x3bbd2，不查表）
   - 单字节 → 渲染层加 0xFF00 前缀（0xA1 → uChar=0xFFA1）传 GDI
   - 默认状态 [esi+0x5b8/0x5c0]=0 时单字节也原样（0x3bb98），查表 0x4bd374 仅特殊模式
   - **GBK 中文首字节大量落在 0xA1-0xDF** → 被拆成两个 0xFFxx → GDI 收到非法 SJIS 码位 → 方框
   - GBK 首字节 0xE0-0xFE 的字 → 双字节原样 → GDI 按 SHIFTJIS 解 → **错误日文字形**（截图「玻」）
4. **运行时 patch1 已生效**：0x3bb08 判定放宽为 0x81-0xFE（GBK 全范围双字节），
   字节读回验证一致。patch 后 GGO 收到 GBK 对（0xECB7/0xF3A3 等），但**显示无改善**。
5. **存在多个解码副本**：`cmp cl,0x81/0x9f/0xe0/0xfc` 序列在 exe 有 3 处
   （0x3bb08 / 0x3a99f / 0x29c0c），patch1 只改了 0x3bb08。
   patch 后 GGO 仍有 0xFFxx（184 次）→ **其余副本未 patch，且用户看到的文本可能走别的副本**。
6. **系统转换函数零调用**（hook 实证）：MultiByteToWideChar（kernelbase/kernel32）、
   RtlMultiByteToUnicodeN、TextOutA/W、ExtTextOutA/W、GetGlyphIndicesA/W **全部 0 次**。
   → 引擎完全自绘渲染（软件 blit），不经过任何系统文本 API。
7. **GetGlyphOutlineA = 引擎取字形路径**：调用点 EXE+0x39c80 / 0x39cc5（每字符 2 次）
   和 EXE+0x39320（直调，无缓存）。函数 0x4039320 无缓存表，字符值来自参数。
8. **日文渲染不走 GGO**：GGO 序列里**从无 0x81-0x9F 开头的 SJIS 值**（0 次），
   日文假名/汉字渲染走引擎自己的位图字库（内嵌数据，未定位）。
   → **日文正常 = 内嵌字库命中；中文乱码 = 字库没有中文字形 + GGO fallback 也错**。
9. **GGO uChar 分布实测**（trace9，patch1 后 528 次）：
   0xFFxx ×184 / SJIS 0xE0-0xEF ×32 / SJIS扩展 0xF0+ ×16 / ASCII ×24 / 其他 ×4，
   0x81-0x9F ×0。
10. **LOGFONT 偏移坑**（重要！）：lfCharSet=**0x17**、lfFaceName=**0x1C**（不是 0x3C/0x20）。
    前几轮 hook 用错偏移 → charset 全部读错/写错位 → 字体 patch 全部无效。
    修正后仍未见游戏的字体创建调用（游戏字体可能经未 hook 的路径创建）。
11. **联网调研**：同引擎 ShiinaRio v2.50 汉化是已解决问题（Nukitashi 2 等）：
    - crskycode LoaderFramework（原仓库已 404）：0x405940 是路径解析函数，用于文件重定向
    - **Yggdrasill-Moe/Niflheim** 的 RioShiina 目录：RioShiina.ini `Version=2500` 正是本引擎，

### 17.1 真因（两条，缺一不可）

**① 引擎把 GBK 汉字首字节拆成单字节 → GDI 收到非法码位**
- 解码器有 **3 个同构副本**：`0x29c0c` / `0x3a9a7` / `0x3bb08`，判定为
  `首字节 0x81-0x9F 或 0xE0-0xFC → 双字节；0xA1-0xDF → 单字节`。
- GBK 常用汉字首字节多在 `0xB0-0xD7`（落在 0xA1-0xDF）→ 被当单字节 → 拆成两个 `0xFFxx`。
- §16.1-4 说"patch1 生效后 GGO 收到 GBK 对（0xECB7/0xF3A3）"是**假象**：
  0xEC/0xF3 本来就在 SJIS 前导范围，**不 patch 也会成对通过**。
  且旧 `gbkfix3.py` 的期望字节写死成 0x3bb08 那一版，另两个副本模式不匹配 → 只改了 1 个。

**② 字体 charset = 128(SHIFTJIS) → GDI 把 GBK 对当 SJIS 解 → notdef**
- `0x3815c` 处 `push 0x80` → `CreateFontA(..., fdwCharSet=128, ...)`（静态确认）。
- GDI 实测（`gdi_glyph_test.py`，ASCII 点阵直读字形）：

| 用例 | 结果 |
|---|---|
| charset128 + GGO_A(0xC4E3) | **2×3 实心块 = notdef** ← 修复前游戏拿到的 |
| charset0   + GGO_A(0xC4E3) | **「你」** |
| charset134 + GGO_A(0xC4E3) | **「你」** |
| charset128 + GGO_W(0x4F60) | **「你」**（W 版不受 charset 影响） |

### 17.9 复盘：为什么 §15/§16 试了很多次没成，本轮一次就中

**根因：§15/§16 的两条核心结论是从"无效实验"里推出来的，而它们本身站不住。**

| 之前的结论 | 为什么错 |
|---|---|
| "GDI 只参与宽度测量，字形渲染不走任何 GDI 文本 API"（§16.1-6） | 唯一依据是 UIF 试金石实验：规则写 `あ→中`。但引擎传的是 **GBK 字节(0xA2D9 之类)**，不是原假名 `あ(0x82A0)`，规则**永远不可能匹配**。§16.1-7 自己已指出"规则必须按错字写"，但没重做实验。 |
| "引擎用内嵌位图字库自绘，日文渲染不走 GGO"（§16.1-8） | 说"GGO 序列里从无 0x81-0x9F 开头的值（0 次）"——但 `work/ggo_seq.txt` 里明明有 `82b3 82ad 82ea 82b1…`（0x82xx=平假名）。观察本身就错了。且**日文正常根本不需要内嵌字库**：CP932 首字节 0x82 本就在 SJIS 前导范围 → 成对通过 → charset128 解 SJIS 正确。一个机制解释全部现象。 |
| "patch1 已生效，GGO 收到 GBK 对（0xECB7/0xF3A3）"（§16.1-4） | **样本选错**：0xEC/0xF3 本来就在 SJIS 前导范围(0xE0-0xFC)，**不 patch 也会成对通过**，天然无法证伪。而 trace9 里 0xFFxx 仍有 **184 个**——这其实是"patch 没生效"的直接证据，却被解释成"字形来自内嵌字库"。 |
| "patch 全部 3 个解码副本"（§16.3 待办） | `gbkfix3.py` 的期望字节序列写死成 `0x3bb08` 那一版的跳转偏移(`74/6a/65`)，另两个副本是 `16/0c/07` → **模式不匹配，只改中 1 个**（日志里 `skip @0x3a9a5 / 0x3a9a7 pattern mismatch`）。 |
| "字体 charset 真值未确认"（§15.2 候选1，方向对但被搁置） | 当时正解就在眼前，但卡在 LOGFONT hook 偏移（§15.1-10 记录 `lfCharSet=0x17` 找错成 0x3C）上，没拿到真值，随后转向 UIF / 逆向内嵌字库。 |

**方法差异（本轮为什么快）**：之前是「**猜机制 → 跑游戏看画面 → 不符再猜**」，每轮 5 分钟且结论模糊；
本轮改成「**静态定位调用点 → 脱离游戏做可判定的 GDI 实验 → 拿到铁证再动刀**」：

1. **静态反汇编先钉死渲染路径**（`pe_scan.py` + `dump_range.py`）：
   - GGO 的 4 个调用点 → 后面跟着 `GlobalAlloc` + 写入 36 字节/条、512 槽的缓存表(`0x53e3d0`)
     → **直接确认"字形来自 GGO"**，一举推翻"内嵌字库"假说。
   - `CreateFontA` 唯一调用点 → `push 0x80` → **charset=128 静态确认**（他们始终没拿到的那个真值）。
   - 3 个解码副本用**带通配掩码的模式搜索**一次找全。
2. **脱离游戏做 GDI 判定实验**（`gdi_glyph_test.py`，ctypes 直调 GGO，字形打成 ASCII 点阵人眼可读）：
   不跑游戏、不导航、不用 UIF，5 分钟得到铁证表（charset128→notdef / charset134→「你」/ GGO_W→「你」）。
3. **用"能否还原原始字节流"做判据**：把 `ggo_seq.txt` 的 uChar 序列按规则还原成字节流——
   GBK 解出正确中文、CP932 解出正确日文 → 一次性证明"GGO 拿到的是原始字节流被 SJIS 规则重新切分的结果"。
4. **顺带排除两个假障碍**：`.text CRC` 自校验（实为启动期自算再比对，自洽 → 静态 patch 安全）；
   字体 ① 不生效的真因（charset=134 时 GDI **静默替换成新宋体**，与"内嵌字库"无关）。

**教训（已升为方法纪律）**：
- **证伪性判据**：验证"补丁生效"时，样本必须**只在该补丁生效时才成立**（0xECB7 这类样本不满足 → 无效验证）。
- **先静态后动态**：能在反汇编里钉死的事实（charset、调用点、字形来源）不要靠"跑游戏+人眼看"去猜。
- **一个机制必须能解释全部现象**：若需要引入"内嵌字库"这类新实体才能自圆其说，先怀疑自己的观察。

### 18.1 陷阱一：单独 rebuild 一个条目，会把其他已翻条目打回日文

**本轮做法**：先把交接文档**全文读完**（§1–§22），再回头验证 §19.9 那条"最高价值目标"。结果发现 **§19.4 的代码归属有两处错误**，但**"28 字崩字"的机理可以用纯字节计算复现**。

### 23.1 ★ 崩字机理：字节级复现（不需要跑游戏）

**核心事实**：L2 那句 = 28 个 GBK 汉字 = **56 字节**。

引擎内部有 **两种解码判定**，切出的"字符单元数"完全不同：

| 判定方式 | L2 切出单元数 | 宽度(×16px) | vs 行宽 640 | 结果 |
|---|---|---|---|---|
| **patch 后**（`0x81`–`0xfe` 全双字节）| **28** | 448 | **不超** | 不换行（期望）|
| **原版 SJIS**（`0x81`–`0x9f` / `0xe0`–`0xfc`）| **46** | **736** | **超** | **换行（实际）** |

**46 × 16 = 736 > 640 → 每行只放 40 个 SJIS 单元 → 换行点落在第 40 单元 = 字节偏移 49 = GBK 第 24 个字。**

**这正好复现了截图**：
```
我把害羞得扭动身体的胡桃的腰用力拉近，舌头更深入地交缠□ r
□
```
- 前 24 字 = `我把害羞得扭动身体的胡桃的腰用力拉近，舌头更深入地交缠`（40 个 SJIS 单元）
- `□ r` = 第 40 单元之后的错位残余（`0xb5`/`0xd8` 等被当独立单字节 → 解出可打印 ASCII 或私用区字）
- 第二行 `□` = 剩余 6 单元（`f8a1` 解出 `\ue640` 私用区 = 字体无此字 → `□`）

**⇒ "28 字换行"不是 28 字，是 46 个 SJIS 单元撑爆 640px。根因是"宽度计算用的解码判定仍是原版 SJIS"。**

### 23.2 ★ 解码器 patch 现状：3 组已 patch，但**另有 1 组 `cmp al` 形式的未确认**

全部 SJIS 双字节判定点（`CHOSAIMIN.EXE`，VA）：

| 组 | `cmp xx,0x81` | 上界 | `cmp xx,0xe0` | `cmp xx,0xfc` | 现状 |
|---|---|---|---|---|---|
| A | `0x43a9a7` | `0x43a9ac`=**0xfe** | `0x43a9b1` | `0x43a9b6` | 已 patch |
| B | `0x43bb08` | `0x43bb0d`=**0xfe** | `0x43bb12` | `0x43bb17` | 已 patch |
| C | `0x429c0c` | `0x429c11`=**0xfe** | `0x429c16` | `0x429c1b` | 已 patch |
| **D** | `0x43ab7e`(`cmp al`) | `0x43ab82`=**0xfe** | `0x43ab86` | `0x43ab8a` | **需确认是否参与宽度** |

另有多处孤立 `cmp al,0x9f`（`0x423d82`/`0x4913e2`/`0x497cf1`/`0x497d5e`）与 `cmp al,0x81`（12 处）不在上述 5 指令序列内，需逐一确认。

**⇒ 关键待办：确认 D 组（`0x43ab7e`，在 `0x3a2a0` 函数内、A 段宽度累加附近）是否就是"宽度计算用的解码判定"。若是且未 patch，就是崩字的直接原因。**

### 23.3 §19.4 代码归属的两处更正

1. **`0x416f2f` / `0x416f48` 调的不是 `0x43a2a0`，而是 `0x4384a0`**（3 指令 getter）。
   只有 **`0x416f42` call `0x43a2a0`** 才是排版主函数入口。
2. **`0x4384a0` 的真身是 `0x4384b0`**：一个**数值解析器**（`ebp`=符号，`esi`=数值，返回 `ebp*esi`），
   解析 `{ 12.5 }` 这类控制码参数；**不是"取下一个字符"**。

### 23.4 `0x438640` = 控制码分派器（不是"逐字绘制循环"）

`0x438640` 取 **1 字节**，`sub ecx,0x28`，`cmp ecx,0x52` → 查字节表 `0x4392c0` → 跳转表 `0x439214`。

- **普通字符**（含所有 GBK 汉字首字节 `0xB0`–`0xD7` → 减 0x28 后 146–191 > 0x52）**走默认出口 `0x439207`，即直接 `ret`，不做任何宽度累加**。
- 跳转表 43 槽中：`slot 17 = 0x4388a0`（= §19.5 的"排版控制码解析器"）；`slot 34 = 0x4386c3`（**换行处理段**：`[esi+0x168]=[esi+0x164]`、`y += [esi+0x17c]`）；`slot 42 = 0x439207`（默认出口）。
- 唯一调用点：**`0x43a7a6 call 0x438640`**（在 `0x3a2a0` 内）。

### 23.5 `0x3a2a0` 是"超大函数"，内含多套宽度代码

`0x3a2a0` 的函数体一直延伸到 `0x3bc6a`（约 6.3KB），里面**同时包含**：

| 段 | RVA | 作用 |
|---|---|---|
| 入口/初始化 | `0x3a2a0` / `0x3b76f` | 写默认值 `[0x178]=8 [0x180]=16 [0x17c]=16 [0x19c]=0x280` |
| **宽度预判 A** | `0x3aa60`–`0x3aac6` | `edi=[esi+0x168]` 起算 + 按类型加宽 → `cmp edi,[esi+0x19c]` 判换行。**不含 `add [esi+0x168]`** |
| **x 推进 B** | `0x3b452`–`0x3b478` | `[esi+0x168] += 16`（汉字）。**全 EXE 仅 3 处 `add [esi+0x168]`：`0x43b469`/`0x43b478`（都在此）/`0x43bc6a`** |

| 控制码分派 | `0x3a7a6` → `0x438640` | 处理 `$`/`{` 等 ASCII 控制符 |

**⇒ 之前以为的"两个函数副本"是错的，实际是"一个函数里两段代码"。**

### 24.2 ★ 三条纵线各自独立，互不一致（崩字的结构性原因）

| 纵线 | 函数 | 它怎么理解字节 | 出问题的地方 |
|---|---|---|---|
| **① 计宽/换行** | `FUN_0043a2a0` `0x3aa5a` 起、`FUN_0043b840` `0x3bc0c` 起 | 用 `[0x81–0x9f]∪[0xe0–0xfc]` 判"是否双字节" | **GBK 汉字首字节 `B0–D7` 落在单字节分支** → 一个汉字只推进 1 个"单元" → `[0x168] += 1×[0x184]`，但下一轮又从第二字节起算，**整体错位** |
| **② 取字形** | `FUN_004395b0` | 把两字节**裸值**合成 16 位（`CONCAT11(b0,b1)`）当码位 | `0xB0D1` 不是合法 Unicode 码位，也不是 CP932 合法码位；GDI 按当前 charset 解释 → **找不到字形** → 空白/方框 |
| **③ 字体** | `FUN_00438100` | `CreateFontA(..., 0x80, ...)` | **charset 硬编码 `0x80` = SHIFTJIS_CHARSET**，与 GBK 无关 |

**关键：这三层没有一个是"宽度算错"那么简单——它们各自用不同规则解释同一串字节。**
即使把①的判定全 patch 成 GBK，②送出的码位依然不是 Unicode，③字体依然按 SJIS 解释。
**这就是"函数都找到了、乱码依然在"的原因**：修一层动不了另外两层。

### 24.3 计宽两种模式的精确定义（读自 `FUN_0043a2a0`）

`FUN_0043a2a0` 里 `param_1 = (pbVar6 + iVar11 + 1) - pbVar6` 即**该字符占的字节数**（1 或 2）；
`puVar7[0x184]` 低 16 位存**码位**。宽度计算分两条支路：

```c
// 支路1：cVar11 == -1（比例字体未启用）
iVar11 = [esi+0x58b] * 字节数;                    // 等宽 × 字节数
if (DAT_00d09bc4 && [esi+0x175]) iVar11 /= DAT_004c21e0;   // DPI 缩放
uVar10 = x + iVar11;
// 支路2：比例字体
if (字节数 == 2) iVar11 = [esi+0x60];
uVar10 = x + iVar11 + [esi+0x61] * 字节数;
if (uVar10 >= [esi+0x67])  →  换行
```

**⇒ 宽度只依赖"字节数"，而"字节数"完全由 ① 的判定决定。**
`[esi+0x67]` = 行宽上限（运行时实测 `0x280`=640）。

**⇒ 要让 text_processor 动起来，`rules` 数组至少要写一条（哪怕是恒等规则）。**


### 29.4 修复

```python
MAX_ANCHORS   = 96     # 最多用多少个注释行做锚点
SPREAD_ORDERS = 8      # 环形旋转变体数（保留搜索多样性）
PER_LINE_HEX  = 256    # 每行最多追加 hex 字符数 → 每行 +512 B
cap = max(1, -(-k // n))                  # ceil(k/n) 均分
```
- **行数依旧零变化**（仍满足 rebuild 硬约束）
- `fitlib.py` 自检各档仍精确命中（tries 2~24，与改动前相当）

### 30.2 `.S25` 容器格式（依据 `arc_unpacker/src/dec/shiina_rio/s25_image_archive_decoder.cc`）
```
"S25\0"
u32 file_count
u32 offsets[file_count]           # 为 0 的槽位跳过
每个 offset 处:
    u32 width; u32 height; 8 字节跳空; u32 flags;
    u32 row_offsets[height]      # ★ 绝对文件偏移（直接 seek 用）
    行数据:  [u16 row_size][row_size 字节载荷]
```
行载荷 token：`u16 tmp` → `method = tmp>>13`，`skip = (tmp>>11)&3`，`count = tmp & 0x7FF`（**count==0 则再读 u32**）

| method | 含义 | 载荷 | 存储序 |
|---|---|---|---|
| 0 / 1 | 空（透明黑），跳过 count 像素 | — | — |
| 2 | RGB 增量，周期 3 累计 | 3×count | R,G,B → 输出 B,G,R,A=255 |
| 3 | RGB 单色重复 | 3 字节 | 同色 count 次 |
| 4 | BGRA 增量，周期 4 累计 | 4×count | **A,B,G,R** → 输出 B,G,R,A |
| 5 | 单色重复 | 4 字节 | **A,B,G,R**，同色 count 次 |

**两条硬约束（踩过坑）**
1. `read_row` 按**绝对行偏移奇偶**决定是否跳 1 字节（`row_size--`）⇒ 编码时必须让所有绝对行偏移为偶数。
2. `decode_row` 每个 token 前 `if (pos & 1) skip(1)` ⇒ token 必须起始于**行载荷内**的偶数偏移（method 4/5 的 token 长度恒偶，天然满足；method 2/3 需补位）。

`flags & 0x80000000` → **incremental** 模式，`decode_row` 的 `repeat` = 共享同一行偏移的条目数（按绝对偏移计数）。
